# Shield Wizard Stable Data Format

Issue: [#19 Stable data format for export/import](https://github.com/Genteure/zmk-wizard/issues/19)

This document is the operating manual for the persisted Shield Wizard data
format. Code lives in [`src/lib/dataFormat.ts`](../src/lib/dataFormat.ts).

## Canonical file

Every repository generated by Shield Wizard contains **one** canonical data
file:

```text
.shield-wizard.json
```

It lives at the repository root, not in `.github/`:

- the data describes the whole generated repository, not just GitHub
  workflows;
- `gh`/GitHub-API tooling (issue #20) should not have to look inside
  GitHub-specific directories;
- `.github/` is conventionally GitHub-owned and may be pruned/ignored by
  third-party tooling.

`createZMKConfig` (in `src/export/index.ts`) adds the file to the generated
files **before** the git pack is created, so it is part of the generated git
commit and travels with the repository.

`buildRepository` (in `src/actions/index.ts`) additionally inserts a **separate
loose tar entry** with the same path after `createGitRepository` returns. That
copy is not part of the git pack; it exists so developers can fetch
`https://host/repo/<id>.git/.shield-wizard.json` for live-service audits and
tests. The two copies serve different purposes: the in-repository file is the
stored config that ships with the repo (and is read back for editing, issue
#20), while the loose endpoint copy is an online audit/test convenience.

## Format version 1

The document is a versioned envelope. `data` is a `Keyboard` as defined by
`KeyboardSchema` in `src/types/keyboard.ts`.

```json
{
  "formatVersion": 1,
  "data": {
    "name": "My Board",
    "shield": "my_board",
    "dongle": false,
    "modules": [],
    "layout": [
      {
        "id": "01J...",
        "part": 0,
        "row": 0,
        "col": 0,
        "w": 1,
        "h": 1,
        "x": 0,
        "y": 0,
        "r": 0,
        "rx": 0,
        "ry": 0
      }
    ],
    "parts": [
      {
        "name": "left",
        "controller": "nice_nano_v2",
        "pins": {},
        "kscans": [],
        "keys": {},
        "encoders": [],
        "buses": {}
      }
    ]
  }
}
```

Rules:

- `formatVersion` is a **positive integer**, bumped by exactly 1 for every
  incompatible change. It is intentionally not called `version` to avoid
  confusion with the Shield Wizard application version.
- `data` must be a JSON object.
- Optional `Keyboard` fields use the defaults declared in
  `src/types/keyboard.ts` (`dongle`, `modules`, `pins`, `kscans`, `keys`,
  `encoders`, `buses`, ...), so a document that omits them is still valid.
- Unknown **top-level envelope** and **top-level `data`** keys are preserved
  across a load → save round trip through the `extensions` mechanism (see
  below). Unknown keys nested inside known objects are **not** guaranteed to
  survive an old reader rewriting the file; see “Unknown fields” below.

## Validation levels

Loading validates in four layers and stops at the first hard failure:

| Layer | Check | Failure behaviour |
| --- | --- | --- |
| 1 | JSON syntax | `ShieldWizardDataJsonError` |
| 2 | Envelope shape (`formatVersion`, object `data`) | `ShieldWizardDataEnvelopeError` |
| 3 | Version gate + migration chain | `UnsupportedDataFormatVersionError` / `UnmigratableDataFormatVersionError` |
| 4 | Structural `KeyboardSchema` validation | `ShieldWizardDataValidationError`, unless partial loading is allowed |

Full business validation (`ValidatedKeyboardSchema` — pin existence, module
conflicts, duplicate wiring, controller limits, ...) is deliberately **not**
run by the data format module. It runs before export/build
(`BuildActions.vue`, `src/actions/index.ts`). A file that opens correctly for
editing can still be invalid for firmware generation; the editor must show
those errors before exporting.

### Partial work (localStorage-like behaviour)

`parseShieldWizardData` defaults to `allowPartial: true`. This is the
“unfinished work can be reopened” behaviour:

- missing optional fields get their schema defaults;
- `name`/`shield` may be empty and `layout`/`parts` may be empty while the
  user is still editing;
- tolerated problems are returned as `issues` with dotted paths, so the UI
  can warn instead of refusing to open the file.

Malformed nested objects (e.g. a key whose `id` is not a ULID) are **not**
silently deleted. They fail structural validation because guessing or
dropping user data is worse than an explicit error.

Callers that expect a complete document (for example, reading the file back
from a generated repository) pass `{ allowPartial: false }`.

## API

```ts
import {
  SHIELD_WIZARD_DATA_FILE,
  CURRENT_DATA_FORMAT_VERSION,
  isShieldWizardDataEnvelope,
  parseShieldWizardData,
  serializeShieldWizardData,
} from '~/lib/dataFormat';

// Load (JSON text or already-parsed value).
const loaded = parseShieldWizardData(text, {
  allowPartial: true,                 // default
  // targetVersion / migrations: injectable for tests
});

// Branch between legacy raw Keyboard JSON and the stable envelope.
const isStable = isShieldWizardDataEnvelope(parsedJson);

loaded.keyboard;              // editable Keyboard state
loaded.originalFormatVersion; // version found in the document
loaded.formatVersion;         // version after migration
loaded.appliedMigrations;     // what ran, oldest first
loaded.issues;                // tolerated structural problems
loaded.extensions;            // unknown keys to pass back on save

// Save. Pass extensions so unknown same-version fields survive editing.
const text = serializeShieldWizardData(loaded.keyboard, {
  extensions: loaded.extensions,
  // allowPartial: true,       // only when deliberately saving a draft
});
```

`serializeShieldWizardData` is strict by default: canonical files must be
complete. Generated repositories are safe because the server validates with
`ValidatedKeyboardSchema` before `createZMKConfig` is called.

### Current consumers

- `src/export/index.ts` — writes the in-repository `.shield-wizard.json` copy
  into the generated file set (committed in the git pack).
- `src/actions/index.ts` — writes the separate loose tar copy served at
  `/repo/<id>.git/.shield-wizard.json` for online developer audit/tests.
- `src/export/contents.ts` — generated README links to `.shield-wizard.json`,
  explains how to load it in Debug Options, and records the Shield Wizard
  commit hash; it does not embed the JSON.
- `src/components/app.vue` — Debug Options → Show Internal Data now shows and
  applies the envelope; it still accepts legacy raw `Keyboard` JSON.
- `scripts/smoke.ts` — accepts fixtures in either legacy raw or stable
  envelope form.
- Issue #20 will call `parseShieldWizardData` when reading a repository file
  with `gh`/the GitHub API.

## Compatibility model

Decide what kind of change you are making **before** touching the format.

### 1. Backward/somewhat-compatible addition — do not bump

Adding an optional field that has a safe default (old readers can ignore it,
new readers can reconstruct the equivalent value from the remaining fields).

Examples:

- adding `part.displayName` that defaults to `part.name`;
- adding an optional cosmetic setting with a default;
- widening a constraint that only rejects previously invalid data.

No `formatVersion` bump. Update the Zod schema with `.default(...)` and add a
round-trip test.

### 2. “Somewhat compatible” change — bump + migrate

Old readers cannot understand documents written by the new format, but the
new reader can transform old documents losslessly.

Examples:

- a new **required** field with a computable default;
- renaming a field;
- moving a field between objects;
- adding a new enum value that persisted data may now contain;
- changing the meaning of a field in a way that has a mechanical conversion.

Procedure:

1. Increment `CURRENT_DATA_FORMAT_VERSION` in `src/lib/dataFormat.ts`
   (e.g. `1 → 2`).
2. Add `defineFormatMigration(oldVersion, 'Description', (envelope) => ...)`
   to `DEFAULT_FORMAT_MIGRATIONS`.
3. The migration receives the **raw envelope** of the old version, deep-copies
   it with `cloneEnvelope`, transforms `data`, and returns the envelope with
   the new `formatVersion`. Never mutate the input; never validate against the
   new `KeyboardSchema` inside the migration (the engine validates after it).
4. Add a test that parses a version `n-1` document, asserts the migrated
   keyboard, and asserts `appliedMigrations`.

Old readers meeting a version-2 document fail closed with
`UnsupportedDataFormatVersionError` (“update Shield Wizard”), which is the
safe behaviour: they must not rewrite data they do not understand.

Old documents are upgraded in memory on load. The next save writes the
current version. If a caller must not silently upgrade a file, it can compare
`loaded.originalFormatVersion` with `loaded.formatVersion` and ask the user
first.

### 3. Completely incompatible change — bump + refuse, never guess

The new reader cannot faithfully convert old data, or old data does not map
onto the new model at all (fundamentally different layout model, removed
feature, changed units where no conversion is possible).

Procedure:

1. Increment `CURRENT_DATA_FORMAT_VERSION`.
2. Add a migration for the old version that returns
   `{ status: 'unsupported', reason: '...' }` with a concrete explanation.
3. The loader throws `UnmigratableDataFormatVersionError` and leaves the
   input untouched. The UI should keep the original file bytes and tell the
   user to keep using an older Shield Wizard (or redo the configuration).

Do **not** write a “best effort” migration that drops fields and hopes. A
rejected document is recoverable; a silently degraded one is not.

## Migration scaffolding reference

Migrations live in `DEFAULT_FORMAT_MIGRATIONS` in `src/lib/dataFormat.ts`.
The registry enforces:

- `to === from + 1` for every migration;
- one migration per source version;
- a cycle/step guard;
- the returned envelope passes `RawEnvelopeSchema` and carries the expected
  `formatVersion`.

Skeleton for the next incompatible bump:

```ts
// Replace 1 and 2 with the actual old and new format versions.
defineFormatMigration(1, 'Describe the change', (envelope) => {
  // If the change cannot be represented safely:
  // return { status: 'unsupported', reason: 'concrete reason' };

  const next = cloneEnvelope(envelope);
  const data = next.data as Record<string, unknown> & {
    parts: Array<Record<string, unknown>>;
  };

  // Old → new transformation example: derive a new required field.
  for (const part of data.parts ?? []) {
    part.requiredNewField = part.oldField ?? 'default';
  }

  return {
    status: 'migrated',
    envelope: { ...next, formatVersion: 2 },
  };
});
```

The migration's `from` version is the **old** `CURRENT_DATA_FORMAT_VERSION`
value (1 in this example); the returned `formatVersion` is the **new** value
you just set on `CURRENT_DATA_FORMAT_VERSION` (2 in this example).

## Unknown fields

`RawEnvelopeSchema` is a Zod loose object (passthrough), and
`parseShieldWizardData` collects unknown top-level envelope keys and unknown
top-level `data` keys into `loaded.extensions`. Passing `extensions` back to
`serializeShieldWizardData` keeps them.

This protects additive top-level changes. It does **not** deep-preserve
unknown fields nested inside known objects. Consequence for format changes:

- A no-bump optional field is only safe if losing it and re-defaulting it
  after an old-reader rewrite is acceptable. Otherwise bump the version so
  old readers fail closed instead of rewriting the file.
- Unknown fields are never trusted: they are carried along, but only the
  known `KeyboardSchema` fields affect the editor/export.

## Pitfalls checklist

- **Read before write.** Never open a file for editing without passing its
  version gate. A newer `formatVersion` means “do not write”.
- **Version gate before data validation.** A future data shape may not parse
  with today’s `KeyboardSchema`; check `formatVersion` first.
- **Migrate raw envelopes, not parsed keyboards.** The target schema may not
  accept the old shape, so parsing first would defeat migrations.
- **Migrations must be pure.** Clone the input, keep ULIDs and cross-references
  intact (`layout[].id` ↔ `parts[].keys`, device IDs ↔ pin usage), and never
  regenerate identifiers.
- **Do not run business validation on load.** It would reject exactly the
  partial states this format exists to preserve.
- **Two copies, two jobs.** The in-repository `.shield-wizard.json` travels
  with the generated repo and is the authoritative copy for editing; the loose
  `/repo/<id>.git/.shield-wizard.json` tar entry is a separate online
  audit/test copy. The README only links to the in-repository file and records
  the generator commit — it does not embed a snapshot that could go stale.
- **Do not rename `formatVersion` to `version`** — the app has a version
  already, and future tooling must be able to detect the data schema
  unambiguously.
- **Do not bump for optional additions with safe defaults**, or every minor
  UI option will fracture the ecosystem of generated repositories.
- **Do not bump the app package version and the format version together** as
  one habit; they change independently.
- **Test both directions.** Add tests for `n-1 → n` migration and for
  `newer-than-supported` rejection whenever you touch the format.
